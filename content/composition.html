Composition vs Inheritance

What is Inheritance?

Let's say we are creating a game with different types of enemies. Some enemies may move differently, others will have a different amount of HP, and some may have different attack patterns altogether. A naive approach would be to make a single script for each single enemy type like so: 


    public class EnemyType1 : MonoBehaviour
    {
        void Attack()
        {
            // Slash
        }
        void Move()
        {
            // Move in a straight line
        }
    }
    
    public class EnemyType2 : MonoBehaviour
    {
        void Attack()
        {
            // Slash
        }
        void Move()
        {
            // Move in a zig-zag pattern
        }
    }

    public class EnemyType3 : MonoBehaviour
    {
        void Attack()
        {
            // Slash
        }
        void Move()
        {
            // Move in a straight line
        }
        void SpecialAttack()
        {
            // Shoot a fireball
        }
    }

However, as you can see in this example, there is a lot of code duplication. If we want to change the way enemies move, we would have to change it in every single script. Not only is this tedious, but it makes adding new enemies more difficult as well. What if there was a way to extract the common behaviors of each enemy type and put them in a base class that all enemies share?

Well, let's do just that. Let's create a base class called Enemy. If each enemy shares the same Move() behavior, then we can add it to this Enemy class. Then, whenever we need to add a new enemy into the game, we can extend it from the base Enemy class like this: 



    public class Enemy : MonoBehaviour
    {
        void Attack()
        {
            // Slash
        }
        void Move()
        {
            // Move in a straight line
        }
    }

    public class EnemyType1 : Enemy
    {
        // Inherits Attack() and Move() from Enemy
    }

    // EnemyType2 and EnemyType3 are hidden for this example, 
    // but they also inherit Attack() and Move() from Enemy

What we effectively did is we made a parent class that defined overarching behavior that all enemies share, and then we create child classes that inherit from it. This is what inheritance means in programming. The child class inherits the behavior of the parent class, and can override it if it needs to.

As you can imagine, this is a much better approach than the first one, because now we can change the Move() behavior in one place, and it will affect all enemies. This is a much more scalable approach to programming, and is a common practice in game development.

Some experienced programmers may be questioning the scalability of this approach. Bear with me here. I will discuss the flaws of inheritance later in this chapter.

But we have a small problem. What if we want an enemy that moves differently than the rest? How can we make it so that we can make a unique Move() function for a child class of Enemy? Well, this is where polymorphism comes in.

Polymorphism

The core concept of polymorphism is this -- let the parent class define the methods that the child class inherits, but allow the child class to override the functionality in the way they want to. For example, let's say we want an enemy to run away from the player instead of chasing them. We can use polymorphism to use the same method signature, but give it different functionality: 



    public class EnemyType2 : Enemy
    {
        void override Move()
        {
            // Move in a zig-zag pattern
        }
    }

    public class EnemyType3 : Enemy
    {
        void SpecialAttack()
        {
            // Shoot a fireball
        }
    }

The child class of a parent does not actually need to override a method for it to implement and use it. If a child does not override the parent method, it will simply inherit the functionality of the parent method.

There are ways to write the parent class that forces any child classes to override a specific method (namely abstract methods), but I do not wish to overload you with additional information.

This can unlock some pretty interesting functionality that can genuinely have beneficial side effects to your code. Since a child object inherits the members defined by its parent, it guarantees that it will have access to the parent's methods. Therefore, we can leverage this fact to make our code adaptable.

Let's say we are making a game where we want the player to be able to interact with multiple kinds of objects. You may think that we can just have a bunch of switch statements to check for the type of object like so: 



    public class PlayerInteraction : MonoBehaviour
    {
        void Interact(GameObject obj)
        {
            switch(obj.GetType())
            {
                case Door:
                    // Do something
                    break;
                case NPC:
                    // Do something else
                    break;
                default:
                    // Do nothing
                    break;
            }
        }
    }

But what if we have 10, 100, 1000 different objects all with their unique functionality and behaviors? This easily becomes unscalable and annoying to deal with. My head hurts just thinking about it. So what can we do?

Remember what I said earlier about inheritance. Inheritance guarantees that all child objects will have a method. So, what we can do is that we can have each child class override an Interact() method, and then we can attach these scripts to each object in the world: 



    public class PlayerInteraction : MonoBehaviour
    {
        void Interact(GameObject obj)
        {
            obj.Interact();
        }
    }

    public class Interactable : MonoBehaviour
    {
        virtual void Interact()
        {
            // Do nothing
        }
    }

    public class Door : Interactable
    {
        void Interact()
        {
            // Open the door
        }
    }
    
    public class NPC : Interactable
    {
        void Interact()
        {
            // Talk to the NPC
        }
    }

Instead of putting unnecessary bug-prone functionality inside of the player's interaction script, we isolated the interaction logic in individual scripts attached to each object. This means that the player's interaction script will work with any object no matter what as long as it inherits from that class. So, what would have been hundreds to thousands of lines of code in a single script now has become divided into separate files, making organization and isolated bug-fixing much easier.

The Problem With Inheritance

As mentioned in an aside, some of you here may have found or have already been made aware of the flaws of inheritance. However, to those still unaware, it's okay! I made the same mistake when I first learned about inheritance in college. That's the purpose of this website after all. However, I do not want you to take away the notion that inheritance sucks. Realistically, it takes knowledge and experience to know when to use inheritance and when not to use it. Hopefully, this section can explain that clearly. If not, you can always open an issue on GitHub!

One of the biggest flaws that come with inheritance is the contract signed between a parent class and its children. In between the twists and turns that come with game development and software engineering as a whole, many things are rarely guaranteed to stay the same. Plans change, code needs to be refactored, and what you thought would remain the same actually has to be reworked. Due to nature of inheritance, if you change the parent class in any way, it is possible that many of the child classes will be affected. This can easily be a nightmare to refactor depending on how large the game is.

For example, what happens if we have a hundred different types of enemies, and we decide that some enemies are unable to move at all? What if you made it where every enemy has an HP variable, but you want an enemy that cannot take damage? Maybe some of them don't even attack the player. How will we handle exceptions to the rules that we established? Sure, we can check for the specific type an object is, but that risks entering the switch statement purgatory that was described previously. This is the pitfall of inheritance; you are signing a contract that forces every single child class to follow the same principles.

So, how do we limit the number of contracts that we sign while still maintaining flexibility in the game design process?

Well, say hello to composition.

Composition as an Alternative

So what makes composition so special? Well, what if instead of having multiple classes and subclasses to handle variations of an enemy, we create separate objects such as MoveSystem, AttackSystem, and HPSystem. That way, we can pick and choose whether an enemy includes these systems.

For example, let's say we have an enemy that cannot move, but they can attack the player. What this would look like is that we would create an Enemy class that has three variables, one for each system. Then, we can create interfaces for each type of system and set each of these variables to these types like so: 



    public class Enemy : MonoBehaviour
    {
        public IMoveSystem moveSystem;
        public IAttackSystem attackSystem;
        public IHPSystem hpSystem;

        void Update()
        {
            if (moveSystem != null)
                moveSystem.Move();
            
            if (attackSystem != null)
                attackSystem.Attack();

            if (hpSystem != null)
                hpSystem.TakeDamage();  
        }
    }

Now, whenever we want to create a new kind of movement system, we can create a new class that implements the proper interface. This allows us to create a new movement system that can be used by any enemy. The best part about this design is that we have a "handler" script and a "dependency" script. The handler script (i.e. Enemy) is the one that uses the dependency script (i.e. MoveSystem). This means that we can change the dependency script without affecting the handler script, and we can reuse these scripts across enemies.

The concept of inserting a dependency into a handler script through external means, such as a manager or through Unity's inspector window, is called Dependency Injection. This is a very common design pattern in software engineering, and it is used to make code more flexible and reusable. I'd definitely recommend looking into it if you are interested in learning more about software engineering and design patterns.

But wait, what's the difference between using an interface instead of a class?

Well, functionally, they're the same. However, an interface is a contract that defines a set of methods that a class must implement, but does not create a hierarchy like a class does. This means that a class can implement muliple interfaces without being forced to inherit from a single parent class. This is a very useful feature that allows for more flexibility in code design.

Conclusion

Does this mean inheritance is completely useless? No, of course not! Sometimes, you want that contract to be made for polymorphism to be used. Polymorphism is very useful when you want one line of code to work for several different types of objects, like one Drive() function call that works for all types of Car types. However, whenever you use inheritance, keep in mind the contract you are making. Like all things, use your knowledge with purpose.
