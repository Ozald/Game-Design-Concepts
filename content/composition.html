Inheritance & Composition

What is Inheritance?

Let's say we are creating an RPG game with different types of enemies. Some enemies may move differently, and some enemies currently have special attacks. However, they share some common behaviors, such as their base attacks. A naive approach would be to make a single script for each single enemy type and copy and paste the code like so: 


public class Knight : MonoBehaviour
{
    void Attack()
    {
        // Slash
    }
    void Move()
    {
        // Move in a straight line
    }
}

public class Assassin : MonoBehaviour
{
    void Attack()
    {
        // Slash
    }
    void Move()
    {
        // Move in a zig-zag pattern
    }
}

public class Mage : MonoBehaviour
{
    void Attack()
    {
        // Slash
    }
    void Move()
    {
        // Move in a straight line
    }
    void SpecialAttack()
    {
        // Shoot a fireball
    }
}

//...

As you can see in this example, there is a lot of code duplication. The Attack() methods are duplicated across all enemy types, and the Move() method is also duplicated across the Knight and the Mage. If we want to change the way all enemies attacked, we would have to change it in each and every single script. For example, if we want to change how all enemies attack, we would have to change it in the Knight, Assassin, and Mage scripts. Not only is this tedious, but it makes adding new enemies more difficult as well. A new enemy would require a new script written from scratch, and we would have to copy and paste the code from one of the existing scripts. For small projects, this may be okay, but as projects grow larger, this becomes unscalable and difficult to maintain.

What if there was a way to extract the common behaviors of each enemy type and put them in a base class that all enemies share?

Well, let's do just that. Let's create a base class called Enemy. In our example, each enemy will have the same Attack() and Move() methods, so we can put those in the base class. Now that we have our base class, we can now extend from that class to create new subtypes of enemies. For example, let's recreate the Knight class: 


public class Enemy : MonoBehaviour
{
    void Attack()
    {
        // Slash
    }
    void Move()
    {
        // Move in a straight line
    }
}

public class Knight : Enemy
{
    // Inherits Attack() and Move() from Enemy
}

What we effectively did is we made a parent class that defined overarching behavior that all enemies share, and then we create child classes that inherit from it. This is what inheritance means in programming. The child class inherits the behavior of the parent class, and can add new functionality if it needs to.

As you can imagine, this is a much better approach than the first one, because now we can change the Move() behavior in one place, and it will affect all enemies. This is a much more scalable approach to programming, and is a common practice in game development.

Some experienced programmers may be questioning the scalability of this approach. Bear with me here. I will discuss the flaws of inheritance later in this chapter.

But we have a small problem. Our Assassin class previously had a unique Move() function in which it moved in a different way than other enemies. What do we do if we want to change the functionality of a specific method in a child class? Well, this is where polymorphism comes in.

Runtime Polymorphism

The core concept of runtime polymorphism is this -- let the parent class define the methods that the child class inherits, but allow the child class to override the functionality in the way they want to. For example, let's say we want an enemy to move in a zig-zag pattern. We can use runtime polymorphism to use the same method signature, but give it different functionality: 


public class Assassin : Enemy
{
    override void Move()
    {
        // Move in a zig-zag pattern
    }
}

The child class of a parent does not need to override a method for it to implement and use it. If a child does not override the parent method, it will simply inherit the functionality of the parent method.

There are ways to write the parent class that forces any child classes to override a specific method (namely abstract methods), but I do not wish to overload you with additional information.

This can unlock some pretty interesting properties that can genuinely have beneficial side effects to your code. For example, since the child class inherits the parent class, it is guaranteed to have access to the parent's methods. As a result, no matter what type of child class you have, you can call the same method on it and it will work. 


Enemy enemyA = new Assassin();
enemyA.Move();       // Calls the overridden Move() method in Assassin

Enemy enemyB = new Knight();
enemyB.Move();       // Calls the Move() method in Knight (inherited from Enemy)

This is an example of runtime polymorphism, where the method that is called is determined at runtime based on the type of object that is being referenced. This allows for more flexible and reusable code, as you can write code that works with any type of object that inherits from a common parent class. This property applies to abstract classes and interfaces as well, which is why they are so useful in programming. Here is how we can leverage runtime polymorphism to make our code more flexible and reusable.

Let's say we are making a game where we want the player to be able to interact with multiple kinds of objects. You may think that we can just have a bunch of switch statements to check for the type of object like so: 


public class PlayerInteraction : MonoBehaviour
{
    void Interact(GameObject obj)
    {
        switch(obj.GetType())
        {
            case Door:
                // Do something
                break;
            case Chest:
                // Do something
                break;
            case Button:
                // Do something
                break;
            case NPC:
                // Do something else
                break;
            default:
                // Do nothing
                break;
        }
    }
}

But what if we have 10, 100, 1000 different objects, each with their unique functionality and behaviors? This easily becomes unscalable and annoying to deal with. Can you imagine how many lines of code you would need in a single script? It's a maintainance nightmare ready to happen. So, how do we solve this problem? Well, we can use runtime polymorphism to our advantage.

Remember what I said earlier about inheritance? The child class inherits all methods of the parent class. So, what we can do is that we can have each child class override an Interact() method, and then we can attach these scripts to each object in the world: 


public class PlayerInteraction : MonoBehaviour
{
    void Interact(Interactable obj)
    {
        obj.Interact();
    }
}

public class Interactable : MonoBehaviour
{
    virtual void Interact()
    {
        Debug.Log("Interacted with an object");
    }
}

public class Door : Interactable
{
    void Interact()
    {
        // Open the door
    }
}

public class NPC : Interactable
{
    void Interact()
    {
        // Talk to the NPC
    }
}

//...

This example is exactly the same to what we did with the enemies earlier. Since the Door and NPC classes inherit from the Interactable class, the compiler knows that they have an Interact() method. So, all we need to do is pass in the object that the player isinteracting with, such as through a collision or a key press. This means that we can call the Interact() method on the Interactable object, and the correct method will be called based on the type of object that is being referenced.

Additionally, instead of putting unnecessary bug-prone functionality inside of the player's interaction script, we isolated the interaction logic in individual classes attached to each object that we can place into different scripts. This means that the player's interaction script will work with any object no matter what as long as it inherits from Interactable So, what would have been hundreds to thousands of lines of code in a single script now has become divided into separate files, making organization and isolated bug-fixing much easier.

The Problem With Inheritance

As mentioned in an aside, some of you here may have found or have already been made aware of the flaws of inheritance. However, to those still unaware, it's okay! I made the same mistake when I first learned about inheritance in the first place. That's the purpose of this website after all. However, I do not want you to take away the notion that inheritance sucks. Realistically, it takes knowledge and experience to know when to use inheritance and when not to use it. Hopefully, this section can explain that clearly. If not, you can always open an issue on GitHub!

One of the biggest flaws that come with inheritance is the contract signed between a parent class and its children. In between the twists and turns that come with game development and software engineering as a whole, many things are rarely guaranteed to stay the same. Plans change, code needs to be refactored, and what you thought would remain the same actually has to be reworked. Due to nature of inheritance, if you change the parent class in any way, it is possible that many of the child classes will be affected. This can easily be a nightmare to refactor depending on how large the game is.

For example, what happens if we have a hundred different types of enemies, and we decide that some enemies are unable to move at all? What if you made it where every enemy has an HP variable, but you want an enemy that cannot take damage? Maybe some of them don't even attack the player. How will we handle exceptions to the rules that we established? Sure, we can check for the specific type an object is, but that risks entering the switch statement purgatory that was described previously. This is the pitfall of inheritance; you are signing a contract that forces every single child class to follow the same principles.

So, how do we limit the number of contracts that we sign while still maintaining flexibility in the game design process?

Well, say hello to composition.

Composition as an Alternative

So what makes composition so special? Well, what if instead of having multiple classes and subclasses to handle variations of an enemy, we create separate objects such as MoveSystem, AttackSystem, and HPSystem. That way, we can pick and choose whether an enemy includes these systems.

For example, let's say we have an enemy that cannot move, but they can attack the player. What this would look like is that we would create an Enemy class that has three variables, one for each system. Then, we can create interfaces for each type of system and set each of these variables to these types like so: 


public class Enemy : MonoBehaviour
{
    public IMoveSystem moveSystem;
    public IAttackSystem attackSystem;
    public IHPSystem hpSystem;

    void Update()
    {
        if (moveSystem != null)
            moveSystem.Move();
        
        if (attackSystem != null)
            attackSystem.Attack();

        if (hpSystem != null)
            hpSystem.TakeDamage();  
    }
}

Now, whenever we want to create a new kind of movement system, we can create a new class that implements the proper interface. This allows us to create a new movement system that can be used by any enemy. The best part about this design is that we have a "handler" script and a "dependency" script. The handler script (i.e. Enemy) is the one that uses the dependency script (i.e. MoveSystem). This means that we can change the dependency script without affecting the handler script, and we can reuse these scripts across enemies. I personally like to think of this as a "plug-and-play" system, where we can plug in different systems to create different behaviors altogether.

The concept of inserting a dependency into a handler script through external means, such as a manager or through Unity's inspector window, is called Dependency Injection. This is a very common design pattern in software engineering, and it is used to make code more flexible and reusable. I'd definitely recommend looking into it if you are interested in learning more about software engineering and design patterns.

But wait, what's the difference between using an interface instead of a class?

Well, functionally, they're the same. However, an interface is a contract that defines a set of methods that a class must implement, but does not create a hierarchy like a class does. This means that a class can implement multiple interfaces without being forced to inherit from a single parent class. This is a very useful feature that allows for more flexibility in code design.

Does this mean inheritance is completely useless? No, of course not! Sometimes, you want that contract to be made so that runtime polymorphism can be used. It is very much a handy feature, after all. Personally, I like to use interfaces instead of parent classes due to their flexibility, but at its core, it is the same concept as inheritance. No matter what you choose, though, make sure you know what you're doing, and that you are using the right tool for the job. Just because you have a hammer doesn't mean everything is a nail.

Conclusion

Overall, both inheritance and composition have their pros and cons. For smaller systems, inheritance can be a good choice, but for larger, more complex systems, composition often provides more flexibility and maintainability at the cost of increased complexity and time to set up. Knowing when to use each approach is a key skill in software engineering and game development. Once you start thinking about game progrmaming not as a series of scripts, but as a series of systems that you need to maintain, your skill as a developer will grow exponentially. I hope this chapter has helped you understand the differences between inheritance and composition, and how to use them effectively in your own projects.
